# 🤔 Векторная БД в PartScout - нужна ли?

Отличный вопрос! Давай проанализируем.

---

## 📊 Анализ необходимости векторной БД

### **Для MVP: НЕ критична ❌**

**Почему:**

```
Текущий workflow:
1. Менеджер: "Масляный фильтр Toyota Camry 2015"
   ↓
2. Catalog-server → exist.ru API
   ↓ (получаем точный артикул)
3. Артикул: 04152-YZZA6
   ↓
4. Browser-server → парсинг по точному артикулу
   ↓
5. Результат: структурированные данные (цена, наличие)

✅ Все работает на точных совпадениях
✅ Каталоги поставщиков структурированы
✅ Exist.ru уже предоставляет аналоги и кросс-номера
```

## 🎯 Когда векторная БД БЫЛА БЫ полезна

### **Сценарий 1: Нечеткий поиск запросов**

```python
# Менеджер пишет с опечатками/сленгом
"тармазные диски пирёдние камри 50"

# С векторным поиском:

```

**НО:** Gemini уже хорошо понимает естественный язык и исправляет опечатки через промпт.

### **Сценарий 3: База знаний и RAG**

```python

# RAG с векторной БД:
1. Ищем в базе знаний о совместимости
2. Находим релевантные документы

```

**НО:** Для MVP это избыточно, каталоги дают точную информацию.

**Это полезно, НО:** Нужна накопленная история заказов (Phase 2-3).

## 💡 Supabase + pgvector - лучшее из двух миров

### **Важно:** Supabase поддерживает векторный поиск БЕЗ отдельной БД!

```sql
-- Включаем расширение pgvector в Supabase
CREATE EXTENSION IF NOT EXISTS vector;

-- Таблица с векторами
CREATE TABLE parts_catalog (
    id UUID PRIMARY KEY,
    article TEXT,
    description TEXT,
    embedding vector(1536)  -- OpenAI/Gemini embeddings
);

-- Индекс для быстрого поиска
CREATE INDEX ON parts_catalog 
USING ivfflat (embedding vector_cosine_ops);

-- Семантический поиск
SELECT article, description
FROM parts_catalog
ORDER BY embedding <-> query_embedding
LIMIT 10;
```

**Преимущества:**
- ✅ Не нужна отдельная векторная БД (Pinecone, Weaviate, Qdrant)
- ✅ Все в одной БД (PostgreSQL + векторы)
- ✅ Меньше инфраструктуры
- ✅ Можем добавить постепенно (не с MVP)

## 🗺️ Roadmap для векторного поиска

### **Phase 1 (MVP): БЕЗ векторов ❌**

```
Причины:
✅ Exist.ru API дает точные артикулы
✅ Парсинг по точным совпадениям
✅ Gemini понимает естественный язык
✅ Нет накопленных данных для обучения
✅ Фокус на core функционал
```

---

### **Phase 2: Подготовка (опционально) ⏳**

```sql
-- Добавляем поле для embeddings в существующие таблицы
ALTER TABLE parts_catalog 
ADD COLUMN description_embedding vector(1536);

-- Начинаем собирать данные:
1. История запросов менеджеров
2. Популярные комбинации деталей
3. Синонимы и сленг
4. Отзывы клиентов о деталях
```

---

### **Phase 3: Активное использование ✅**

**Когда имеет смысл:**
- ✅ Накоплено >1000 уникальных запросов
- ✅ Есть история заказов для рекомендаций
- ✅ Нужен поиск по неструктурированным данным
- ✅ Хотим добавить чат-бота с базой знаний

**Кейсы использования:**

```python
# 1. Умный поиск
@mcp_server.tool()
async def semantic_search(query: str) -> List[Part]:
    """Нечеткий поиск деталей"""
    embedding = await get_embedding(query)  # Gemini embeddings
    results = await supabase.rpc(
        'match_parts',
        {'query_embedding': embedding, 'match_threshold': 0.8}
    )
    return results

# 2. Рекомендации
@mcp_server.tool()
async def recommend_related_parts(article: str) -> List[Part]:
    """Что обычно покупают вместе с этой деталью"""
    part_embedding = await get_part_embedding(article)
    similar_orders = await vector_search(part_embedding)
    return extract_recommendations(similar_orders)

# 3. RAG для вопросов
@mcp_server.tool()
async def answer_compatibility_question(question: str) -> str:
    """Ответ на вопрос о совместимости деталей"""
    # Ищем релевантные документы в векторной БД
    docs = await semantic_search_docs(question)
    
    # RAG с Gemini
    context = "\n".join([doc.content for doc in docs])
    answer = await gemini.generate(
        prompt=f"Контекст: {context}\n\nВопрос: {question}"
    )
    return answer
```

## 🎯 ИТОГОВАЯ РЕКОМЕНДАЦИЯ

### **Текущий стек (MVP):**

```yaml
Хранилище данных:
  ✅ Supabase PostgreSQL:
      - Структурированные данные (артикулы, цены, заказы)
      - Кэш (цены с TTL)
      - История запросов (текст)
      - Справочники
  
  ❌ Векторная БД: НЕ используется
  
  ⏳ pgvector (резерв):
      - Расширение уже доступно в Supabase
      - Можем включить когда понадобится
      - Без дополнительной инфраструктуры
```

### **Когда добавим векторы:**

```
Триггеры для включения:
1. 📊 >1000 запросов в истории
2. 🤔 Частые вопросы о совместимости
3. 🎯 Нужны персональные рекомендации
4. 🔍 Менеджеры часто пишут с опечатками
5. 📚 Хотим базу знаний (RAG)
```

## 📋 Обновленный стек

### **Было (моя первая версия):**
```
Storage:
├── PostgreSQL (основное)
├── Redis (кэш)
└── S3 (файлы)
```

### **Уточненная версия:**

```yaml
Data Layer:
  Supabase PostgreSQL:
    - Основные данные (JSONB для гибкости)
    - Кэш с TTL (без Redis для MVP)
    - pgvector (отключен, готов к включению)
  
  Supabase Storage:
    - PDF отчеты
    - Скриншоты
    - Логотипы поставщиков
  
  Опционально (Phase 2+):
    - Redis (если нужна high-performance кэш)
    - pgvector (для семантического поиска)
```

## 💬 Вывод

### **Для PartScout MVP векторная БД НЕ нужна, потому что:**

1. ✅ Exist.ru API дает точные артикулы и аналоги
2. ✅ Поиск идет по структурированным данным
3. ✅ Gemini понимает естественный язык без embeddings
4. ✅ Нет накопленной истории для обучения
5. ✅ Фокус на core функционал (парсинг + анализ)

### **НО мы готовы к масштабированию:**

- 🔄 Supabase уже поддерживает pgvector
- 🔄 Можем включить когда накопим данные
- 🔄 Без изменения инфраструктуры
- 🔄 Постепенная миграция (не "big bang")
